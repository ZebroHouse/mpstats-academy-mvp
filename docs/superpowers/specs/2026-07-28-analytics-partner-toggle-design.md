# Спека: тумблер «партнёрский трафик» в аналитике

**Дата:** 2026-07-28
**Тип:** feat(analytics) — фильтр партнёрского канала в админ-аналитике
**Приоритет:** средний
**Статус:** готово к планированию
**Ветка (предлагаемая):** `feature/analytics-partner-toggle`

---

## Проблема (подтверждено на данных 2026-07-28)

Половина июльских регистраций (232 из 460 за 1–23 июля) пришла через партнёрский канал на бесплатный курс инструментов MPSTATS. Эти пользователи регистрируются ради бесплатного курса и в массе не покупают платформу. Сейчас **аналитика считает их вперемешку с органикой** — тумблера включить/исключить партнёрский трафик нет нигде (проверено грепом: в `admin-analytics*.ts` и админ-компонентах — ноль упоминаний partner). Из-за этого верх воронки раздут, а конверсия триал→оплата занижена.

**Сигнал надёжный:** партнёрская регистрация помечена durable-меткой в Supabase auth — `auth.users.raw_user_meta_data->>'partner_source' = 'mpstats'` (ставится в `createPartnerUser`, `apps/web/src/app/api/partner/mpstats/enter/route.ts`). Метка сделана именно для того, чтобы этих юзеров можно было выделить.

## Решение

### 1. Зеркалим метку в `UserProfile` (рекомендуется)

Метка живёт в `auth.users` (схема Supabase auth), а вся аналитика ходит Prisma по `UserProfile`/`Subscription`/`Payment`. Чтобы фильтр был чистой однострочной добавкой рядом с существующим `isTest: false`, **добавляем аддитивную колонку `UserProfile.isPartnerEntry Boolean @default(false)`** — по образцу `isTest`.

- Миграция аддитивная, через Mgmt API tsx-скриптом (localhost смотрит в прод), порядок «миграция → generate → код». См. `.claude/memory/reference_supabase_migration_via_mgmt_api.md`.
- Проставлять в partner-entry: одна строка в `upsertPartnerProfile` (`.../mpstats/enter/route.ts`) — `isPartnerEntry: true` в create/update.
- **Бэкфилл:** `UPDATE "UserProfile" SET "isPartnerEntry"=true WHERE id IN (SELECT id::text FROM auth.users WHERE raw_user_meta_data->>'partner_source'='mpstats')` — 232 юзера на момент написания.

Альтернатива без миграции — raw-join к `auth.users` в каждой аналитической процедуре. Отвергнута: дублирует join по всем процедурам, медленнее, несогласованно с паттерном `isTest`. Зеркальная колонка предпочтительна.

### 2. Тумблер в UI

В строке фильтров аналитики (рядом с `AnalyticsDateRange`, `apps/web/src/components/admin/AnalyticsDateRange.tsx`) — переключатель **«Партнёрский трафик: учитывать / не учитывать»**. Состояние локальное на странице (как диапазон дат, общего провайдера нет). Прокидывается в tRPC-запросы как булев параметр `includePartner`.

**По умолчанию — ВЫКЛЮЧЕН** (партнёрский трафик НЕ учитывается): продуктовые метрики по умолчанию показывают органику, а не бесплатный курс. Owner может включить, чтобы увидеть полную картину.

### 3. Применение фильтра

Правило простое: **тумблер работает так же, как исключение тестовых, но управляемо.** Когда «не учитывать» — к DB-запросам добавляется `isPartnerEntry: false` рядом с `isTest: false`.

Затрагиваемые процедуры (`packages/api/src/routers/admin-analytics.ts` + `admin-analytics-funnel.ts`): `getConversionFunnel`, `getTrialConversion`, `getActiveUserStats`, `getProductFunnel` (DB-часть: триал/оплата), реестр клиентов (`sales-registry.ts`). Входная схема этих процедур получает опциональный `includePartner: z.boolean().default(false)`.

**Нюанс, зафиксировать явно:** в табе «Продуктовая воронка» шаги из Метрики (визиты, регистрация-goal и т.д.) тумблер **не меняет** — партнёрский вход создаёт юзера server-side, минуя клиентскую страницу регистрации, где стреляет `reachGoal('platform_signup')`, так что Метрика-цель партнёрских в массе и не считает. Тумблер влияет на **DB-производные** шаги (триал, оплата) и на старый таб «Воронка»/«Клиенты». Это правильно и это надо подписать в UI, чтобы не путало.

**Выручку не трогаем** — партнёрские не платят, искажения нет; применять там фильтр бессмысленно (но безвредно, если ляжет сквозняком — на усмотрение плана).

## Границы

**Не делаем:** разбивку по каналам/UTM (атрибуция Метрики 6–22%, отдельная задача); отдельный «партнёрский» дашборд; исключение партнёрских из чего-либо, кроме аналитики (в самом продукте они полноправны).

## Открытый вопрос для owner (решить на плане)

Тумблер режет **только регистрацию + воронку** (где партнёрские искажают) или **все метрики аналитики сквозняком**? Рекомендация — везде, где сейчас исключаются тестовые (единое правило, меньше сюрпризов).

## Проверка

1. Миграция → `prisma generate` → `pnpm typecheck` + `pnpm --filter web build`.
2. Бэкфилл dry-run: счётчик = 232 (сверить с `SELECT count(*) FROM auth.users WHERE raw_user_meta_data->>'partner_source'='mpstats'`).
3. Аналитика: тумблер OFF → регистраций за 1–23 июля 228 (органика); ON → 460 (всего). Сверить с ручным SQL из этой сессии.
4. Новый партнёрский вход → `isPartnerEntry=true` в `UserProfile`.
