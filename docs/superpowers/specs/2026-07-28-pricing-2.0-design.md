# Спека: Тарифы 2.0 — снести мёртвый COURSE, добавить объёмные скидки 3/6 мес

**Дата:** 2026-07-28
**Тип:** feat(billing) — реструктуризация тарифов
**Приоритет:** высокий
**Статус:** готово к планированию (деньги — реализация только через дизайн-ревью)
**Ветка (предлагаемая):** `feature/pricing-2.0-multimonth`

## 1. Задача и решения owner'а

**Проблема:** тариф COURSE (1990 ₽/курс) мёртв — на проде **0 активных COURSE-подписок** (5 CANCELLED, 7 EXPIRED, 15 PENDING, ни одной ACTIVE/TRIAL на 2026-07-27). Диагноз: он не «без спроса», а **запаролен относительно PLATFORM** — 1990 за один курс против 2990 за всё — и каннибализирует себя ценой.

**Решения owner'а (зафиксированы в обсуждении 2026-07-27/28, не переоткрывать):**
1. **COURSE сносим полностью.** Одиночного входа «за курс» не будет — платформа становится единственным продуктом.
2. **PLATFORM 2990/мес остаётся базой.** Добавляем объёмные скидки за длинные периоды:

   | Период | Цена | В месяц | Выгода | Подача |
   |---|---|---|---|---|
   | 1 мес | 2 990 ₽ | 2 990 | — | по умолчанию |
   | 3 мес | 7 990 ₽ | 2 663 | −11% | «выгоднее на 11%» |
   | 6 мес | 13 990 ₽ | 2 332 | −22% | «месяц в подарок» + пометка «выгодный» |

   Механика: списываем всю сумму периода **сразу**, рекуррент выставляем **на тот же период** (3 мес → списание раз в 3 мес по 7990; 6 мес → раз в 6 мес по 13990). Скидка постоянная (рекуррент по цене периода).
3. **Акция «2 месяца по цене одного» остаётся** как есть — разовый триггер конверсии из триала (оплата 1 мес по полной во время триала+24ч → бонусный месяц → через 60 дней помесячный рекуррент 2990). Живёт **параллельно** мультимесяцу, не конфликтует: акция — только на 1-месячном пути.
4. Цены — продуктовая гипотеза; в БД редактируемы, менять без деплоя.

## 2. Архитектурное решение: мультимесяц = отдельные PLATFORM-планы по `intervalDays`

**Выбрано (Option A):** каждый период — отдельная строка `SubscriptionPlan` типа PLATFORM с разным `intervalDays`/`price`:
- PLATFORM / 2990 / `intervalDays=30` (существует)
- PLATFORM / 7990 / `intervalDays=90` (новый)
- PLATFORM / 13990 / `intervalDays=180` (новый)

**Почему так.** Существующая машина уже делает ровно «полная сумма периода вперёд + рекуррент по цене периода»: первый период = `offerFirstPeriodDays ?? plan.intervalDays` (`subscription-service.ts:64-72`), рекуррент-сумма = `plan.price` (`billing.ts:324`), продление = `plan.intervalDays` (`decide-recurrent-update.ts:52`). Для 3/6-мес плана это **автоматически** даёт списание 7990 за 90 дней и рекуррент 7990 каждые 90 дней — без нового биллингового механизма. Цены остаются в БД (редактируемы одним UPDATE, как сейчас).

**Отвергнуто (Option B):** один PLATFORM-план + параметр `periodMonths` с прайс-таблицей в коде. Причина: уводит цены из БД в код (нельзя менять без деплоя), ломает принцип «цена — данные».

**Цена решения:** резолв «единственного PLATFORM-плана» перестаёт работать — сейчас всюду `findFirst({ type:'PLATFORM', hidden:false, isActive:true })` (`billing.ts:153`) и `plans.find(p => p.type==='PLATFORM')` (`billing/page.tsx:140`). Теперь PLATFORM-планов три. Резолв — по паре `(type, intervalDays)`; UI получает селектор периода.

## 3. Изменения по слоям

### 3.2. Резолв плана + `initiatePayment` (`billing.ts:117-335`)

- Удалить COURSE-ветки: валидацию `courseId` (:137-148), COURSE в `receipt` (:182-193, :281-283), `getApplicableDiscount` enum (:76), дропдаун `getCourses` (:27-33) — если он только для COURSE-покупки.

### 3.3. CloudPayments рекуррент-период (ЛИНЧПИН — параметризовать)
Рекуррент-объект собирается **на клиенте**, период захардкожен `interval:'Month', period:1` в **двух** местах:
- `apps/web/src/app/pricing/page.tsx:315-322`
- `apps/web/src/app/(main)/billing/page.tsx:198`

Параметризовать по периоду плана: 30д→`{interval:'Month',period:1}`, 90д→`{period:3}`, 180д→`{period:6}`. `recurrentAmount` = `plan.price` периода (уже приходит из API). `startDate` — существующая логика `recurrentStartDate` (`billing.ts:306-319`) работает и для длинных (первый рекуррент через `firstPeriodDays`).
- **54-ФЗ:** `recurrentReceipt` строится на `plan.price`+`plan.intervalDays` (`billing.ts:273-278`) → для длинного плана автоматически 7990/90д. Проверить, что сумма/период в чеке рекуррента = сумме/периоду длинного плана.

### 3.4. UI тариф-страниц (`/pricing` unauth + `/billing` in-product)
- **Одна акцентная PLATFORM-карточка** с селектором периода 1/3/6 мес внутри (не три отдельных тарифа). Месячный выбран по умолчанию; 6-мес помечен «выгодный»; для длинных показываем общую сумму, цену/мес и выгоду («месяц в подарок» для 6 мес).
- **Убрать COURSE-карточки:** `pricing/page.tsx:416-497` (там же захардкоженная строка `1 990 ₽` :429 — удалить), `billing/page.tsx` COURSE-блок; `COURSE_SHORT_LABEL`/`COURSE_FEATURES`/`COMPARISON_ROWS` (`pricing:36-66`, `billing:23-37`) — вычистить или переработать под один продукт.
- `handlePayment` (`pricing:294`) — вместо `planType:'COURSE'|'PLATFORM'` передаёт период.

### 3.5. Акция «2 месяца» — ограничить 1-месячным планом
`resolveApplicableOffer` (`packages/api/src/services/offer/resolve.ts:38-92`) уже гейтит `planType==='PLATFORM'` (:46) и `suppressForDiscount` (:47). **Добавить условие: только `intervalDays===30`** — акция не применяется к 3/6-мес (там уже объёмная скидка + commitment). Так две механики не пересекаются: акция = 1-мес путь, объёмная скидка = 3/6-мес пути. Флаг `OFFER_ENABLED` не трогаем.

### 3.6. Скидочные промокоды — проверить на мультимесяце
`resolveApplicableDiscount` (`services/discount/resolve.ts`) — `planType===null` = «любой план» (:62). Скидка на первый платёж, рекуррент по `plan.price` (линчпин). Для 3/6-мес плана это даёт: первый платёж = скидочный от 7990/13990, рекуррент = 7990/13990. **Работает без изменений**, но: (а) проверить precedence discount>offer на длинных планах (offer там и так выключен по 3.5); (б) `consume-discount.ts:8-14` (`paidAmount < planPrice`) — `planPrice` должен быть ценой ВЫБРАННОГО периода, а не всегда 2990.
