# Спека A: Журнал событий контента и трекинг устройств

**Дата:** 2026-08-06
**Статус:** дизайн согласован, план не написан
**Запрос:** команда методологов, [документ](https://docs.google.com/document/d/1_x38j4v-EFC5C_T_gcSYn7pyuF5njoqajkaXML4JYio/edit) + отдельный список метрик по устройствам

---

## Место в общей картине

Запрос методологов разбит на три спеки:

| Спека | Содержание | Зависимости |
|-------|-----------|-------------|
| **A (эта)** | Сбор данных: журнал просмотров + устройства | — |
| B | Дашборд «Контент 2.0»: курсы/уроки/пользователи, фильтры, экспорт | частично A |
| C | Дашборд «Устройства»: 9 метрик из списка | A + Метрика |

A деплоится первой и отдельно: журнал копит данные, пока делаются дашборды. Иначе на момент готовности UI все графики пустые.

## Проблема

Текущая модель `LessonProgress` (`packages/db/prisma/schema.prisma:256`) — снапшот состояния, не журнал:

- одна строка на пару `(pathId, lessonId)`, ключ `@@unique([pathId, lessonId])`;
- `watchedPercent` — максимум за всё время, никогда не уменьшается;
- нет `createdAt` / `updatedAt`, нет счётчика открытий, нет истории.

Из этого невозможно посчитать: количество открытий, повторные открытия, динамику по дням, активное время просмотра, порядок прохождения уроков, точку отвала. Устройство не пишется нигде.

## Решение

Три аддитивные сущности плюс запись в двух местах.

### Модель данных

#### `ContentView` — строка на каждый заход в урок

```prisma
/// Журнал заходов в урок. Строка на каждое открытие (не на пару юзер-урок).
/// Без FK — как UserActivityDay: защита от каскадов на общей прод-БД.
/// courseId и contentType денормализованы намеренно: почти каждый запрос
/// аналитики группирует по курсу, а копия ещё и фиксирует исторический факт
/// (урок мог переехать в другой курс или сменить тип после просмотра).
model ContentView {
  id            String   @id @default(cuid())
  userId        String   // = UserProfile.id
  lessonId      String
  courseId      String
  contentType   String   // VIDEO | TEXT | INTERACTIVE — снимок на момент захода
  device        String   // MOBILE | TABLET | DESKTOP | UNKNOWN
  activeSeconds Int      @default(0)
  maxPercent    Int      @default(0)
  completed     Boolean  @default(false)
  startedAt     DateTime @default(now())
  updatedAt     DateTime @updatedAt

  @@index([lessonId, startedAt])
  @@index([courseId, startedAt])
  @@index([userId, startedAt])
  @@index([startedAt])
}
```

#### `UserDeviceDay` — устройства пользователя по дням

```prisma
/// Один пользователь за день может дать несколько строк — это и есть сигнал
/// «переходы между устройствами». Отдельная таблица, а не колонка в
/// UserActivityDay: там PK (userId, day), устройство сломало бы уникальность.
model UserDeviceDay {
  userId    String
  day       DateTime @db.Date
  device    String   // MOBILE | TABLET | DESKTOP | UNKNOWN
  createdAt DateTime @default(now())

  @@id([userId, day, device])
  @@index([day])
}
```

#### `DiagnosticSession.device` — новая необязательная колонка

`device String?` — чтобы «устройство во время диагностики» бралось из факта, а не восстанавливалось сопоставлением по дате.

### Определение устройства

Чистая функция в `packages/shared`, разбирающая `ctx.userAgent` на четыре значения: `MOBILE | TABLET | DESKTOP | UNKNOWN`.

`device` и `contentType` хранятся как `String`, а не Prisma-`enum`, намеренно: добавление значения в enum — это DDL против прод-базы, а добавление значения в строковую колонку — обычный деплой. Валидация на входе, в zod-схеме мутации.

Без новой зависимости: библиотеки парсинга User-Agent тянут таблицы моделей телефонов, которые нам не нужны. Функция чистая — покрывается юнит-тестами.

`ctx.userAgent` уже прокидывается в контекст tRPC (`packages/api/src/trpc.ts:17`), правок в контексте не требуется.

### Поток записи

**Устройство** — в хартбите `protectedProcedure` (`packages/api/src/trpc.ts:38`), рядом с существующим upsert `UserActivityDay`. Тот код уже дебаунсится пятью минутами и завёрнут в собственный `catch`; второй upsert рядом не меняет ни поведения, ни профиля нагрузки. На клиенте — ноль правок.

**Просмотры** — отдельная пара мутаций в своём неймспейсе:

- `startView({ lessonId })` → создаёт строку, возвращает `viewId`. Вызывается один раз при открытии страницы урока.
- `pingView({ viewId, activeSeconds, percent, completed })` → обновляет строку. Раз в минуту и один раз при уходе со страницы.

**Не встраивается в существующий `updateProgress`** (`packages/api/src/routers/learning.ts:1031`). У того метода логика «без регрессий»: он держит максимум процента и не откатывает `COMPLETED`. Это верно для состояния и неверно для журнала — журналу нужен честный факт каждого захода, включая тот, где посмотрели меньше, чем в прошлый раз. Совмещение сделало бы из метода две сущности сразу.

**Идемпотентность `startView`.** Если у пары `(userId, lessonId)` самая свежая строка имеет `updatedAt` не старше 2 минут — метод возвращает её вместо создания новой. Гасит двойной монтаж в React и случайный рефетч, но не мешает засчитать реальный повторный заход.

**Накопление секунд.** Плеер считает время только во время воспроизведения: пауза, сворачивание вкладки и уход в фон время не набирают. Для `TEXT` / `INTERACTIVE` уроков (нет плеера) считается время на странице при видимой вкладке. Тип контента лежит в строке, поэтому дашборд обязан сегментировать по нему и никогда не усреднять видео вместе с текстом.

Пинг присылает **накопленное с начала просмотра**, а не дельту: потерянный пинг тогда не теряет данные, следующий их догоняет. `activeSeconds` и `maxPercent` пишутся как максимум от текущего и присланного — защита от гонки пингов.

### Отказы

Журнал — побочный эффект, не имеющий права уронить урок:

- `startView` при ошибке возвращает `null`; клиент это видит и не пингует. Пользователь смотрит урок и ничего не замечает.
- Ошибки логируются, не пробрасываются. Паттерн — как у `userActivityDay.upsert` в `trpc.ts`.
- Рубильник `CONTENT_JOURNAL_ENABLED` (как `EMERGENCY_BANNER_ENABLED`, `OFFER_ENABLED`): выключается переменной окружения и `up -d web`, без отката кода.

### Миграция

Три изменения строго аддитивные: две новые таблицы, одна необязательная колонка. Существующих данных не трогают.

Накат — через Management API по `reference_supabase_migration_via_mgmt_api.md`. **`prisma db push` против этой базы не запускается** (инцидент 2026-05-12, см. `MAAL/CLAUDE.md`).

**Порядок обратный привычному: сначала миграция, потом код.** Наоборот нельзя — задеплоенный код сразу начнёт писать в несуществующую таблицу, и хартбит будет сыпать ошибками у каждого пользователя.

## Что осознанно не делаем

- **Не храним IP и полный User-Agent.** Журнал отвечает на вопрос «кто, что и как долго смотрел», а не «с какого устройства заходил конкретный человек в 14:37». Второе не нужно, а хранить его — без причины набирать персональных данных.
- **Не пишем строку на каждый тик плеера.** Рассматривался вариант с пульсом раз в 30 секунд ради честного активного времени — отвергнут: даёт ~20 строк на просмотр вместо одной, а ту же точность даёт накопление на клиенте.
- **Не делаем предагрегацию в дневные таблицы.** Рассматривался вариант «сырой лог + ночной крон в `ContentStatDay`». При нынешнем объёме (~800 пользователей, оценка ~300 тыс. строк в год) прямые группировки с индексами работают, а крон и лаг в сутки — сложность вперёд. Переход на предагрегат позже не потребует переписывать дашборд: агрегат встаёт под те же запросы.
- **Не ставим внешние ключи.** При удалении урока его просмотры останутся сиротами — это осознанный выбор: аналитика не должна терять историю при чистке контента, а каскады на этой базе уже стоили 24 таблицы.
- **Никакого UI.** Дашборды — спеки B и C.

## Фильтрация тестовых пользователей

Журнал пишет всех, включая `isTest` и админов. Исключение — на чтении, как в Phase 63 и в существующей аналитике. Причина: отфильтровав на записи, мы не сможем передумать; отфильтровав на чтении — сможем.

Известный каветат в проде: счётчик `EmergencyBlockEventDay` тестовых не исключает. Здесь эту ошибку не повторяем.

## Тесты

Vitest, `packages/api/src/routers/__tests__/` — покрываем то, где ошибка тихая и всплывёт через месяц кривыми цифрами:

1. **Разбор User-Agent** — iPhone, Android-планшет, Windows-десктоп, пустое значение.
2. **Окно дедупликации `startView`** — повтор через минуту возвращает ту же строку, через три минуты создаёт новую.
3. **Накопление секунд** — пинг с меньшим значением не уменьшает накопленное; пропущенный пинг догоняется следующим.
4. **Изоляция отказов** — упавшая запись журнала не роняет ни хартбит, ни открытие урока.

Не покрываем: тривиальные upsert-ы и то, что ловится типами.

## Признак готовности

На staging воспроизводится:

1. Открыл урок с телефона, посмотрел 2 минуты, ушёл → в `ContentView` одна строка, `device = MOBILE`, `activeSeconds` близко к 120 (а не ко времени открытой вкладки).
2. Открыл тот же урок повторно → вторая строка, первая не переписана.
3. Заходил с телефона и с ноутбука → в `UserDeviceDay` за день две строки.
4. Прошёл диагностику → `DiagnosticSession.device` заполнен.
5. `CONTENT_JOURNAL_ENABLED=false` → ничего не пишется, платформа работает как сейчас.

Проверяется запросами к базе. UI в этой спеке нет — в этом и смысл этапа.

## Честная рамка для методологов

**Журнал работает только вперёд.** На день включения счётчики открытий, повторов, активного времени и переходов между устройствами равны нулю и наполняются с этого момента.

Ретроспективно из `LessonProgress` восстанавливается только глубина просмотра и факт завершения — то, что лежит там снапшотом. Ни одного открытия, случившегося до запуска, мы не увидим никогда.

Что это значит по пунктам их документа:

| Раздел ТЗ | Доступно сразу (из `LessonProgress`) | Только вперёд (из журнала) |
|-----------|--------------------------------------|----------------------------|
| 1.1 Охват и частота | уники по курсу, среднее/медиана открытых уроков на юзера | количество открытий, повторные открытия, динамика по дням/неделям/месяцам |
| 1.2 Глубина просмотра | средний/медианный %, распределение, доли 20/50/80/100, сравнение уроков | активное время просмотра, повторные просмотры |
| 1.3 Завершение и отвал | завершившие ≥1 урок, среднее завершённых, остановки до 20/50/80% | порядок прохождения, точка отвала, «последний материал перед уходом» |
| 2. По пользователям | имя, email, статус доступа, дата регистрации | дата первой и последней активности **с контентом** |
| Устройства (все 9) | — | всё |

## Разграничение с Яндекс.Метрикой (важно для спеки C)

Часть метрик из списка по устройствам приходит не отсюда, а из Метрики — она уже считает глубину сессии, возвраты и долю устройств по всему трафику, и видит неавторизованных, которых наша таблица не видит вовсе.

**Две половины не сойдутся по числам.** Метрика считает визиты по всему домену `mpstats.academy` (см. `METRIKA_PLATFORM_FILTER` и известную гочу про завышение втрое), наша таблица — авторизованных пользователей платформы. В UI они должны идти раздельными блоками с подписью источника, иначе методологи сложат несводимое.

Распределение источников:

| Метрика | Источник |
|---------|----------|
| Доля мобильных и десктопных сессий | Метрика (весь трафик) + `UserDeviceDay` (авторизованные) |
| Устройство первого входа | `UserDeviceDay` (минимальный день) |
| Устройство во время диагностики | `DiagnosticSession.device` |
| Устройство во время первого полезного действия | `ContentView.device` (первый просмотр) |
| Конверсия в оплату по устройствам | `UserDeviceDay` + `Payment` |
| Отвал по этапам и типу устройства | `ContentView` + `UserDeviceDay` |
| Глубина сессии | Метрика (`ym:s:pageDepth`) |
| Возвраты | Метрика (новые / вернувшиеся) |
| Переходы между устройствами | `UserDeviceDay` (>1 устройство у пользователя) |
